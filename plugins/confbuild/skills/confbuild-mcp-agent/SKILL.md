# confBuild MCP Agent

Use the confBuild MCP server as deterministic project, validation, rendering, and export infrastructure. The connected model performs all planning, geometry decisions, and screenshot analysis.

## Physical materials for AI-generated models

Every generated physical part must carry an appropriate library `mechanicalMaterialId` separately from its visual `material` colour/recipe, including child sheets and parts generated by scripts. A colour, `surface=...`, a part name or a price-estimator default is not a physical-material assignment. Use the actual material family and grade where known; concrete/paving must not inherit steel, and coatings do not replace the substrate. Read the current material library before choosing IDs.

Record a chosen but unverified grade as an assumption in `metadata_json` (`materialStatus: "assumed"`, `materialBasis: "..."`). If the material is genuinely unknown or the library has no suitable entry, leave the ID unset, record `materialStatus: "unknown"` plus the reason, and report it as unresolved; never select an unrelated material merely to fill the field. Purchased/imported multi-material assemblies need verified constituent material data or an explicit unresolved material declaration, not one fictitious bulk material: set `mechanicalMaterialId: "unresolved"` with `materialStatus: "purchased-assembly"` on their rows and state the manufacturer's datasheet mass as `weightKg` on one row (validation reports `PURCHASED_ASSEMBLY_MASS_MISSING` otherwise; `unresolved` on a manufactured row is `PHYSICAL_MATERIAL_MISSING`). Render colours in imported files do not establish physical material.

Before completion, inspect the resolved BOM/material assignment for all physical parts, including configurable variants and nested instances. Resolve `PHYSICAL_MATERIAL_MISSING`, `PHYSICAL_MATERIAL_IS_APPEARANCE` and `PHYSICAL_MATERIAL_FORMULA_UNVERIFIED` findings or report the affected parts as unresolved; never claim complete material/cost/mass coverage while they remain. Helpers, cutters, annotations and pure assembly references are exempt. For edits, preserve known assignments and repair the generated/changed parts within task scope.

## One drawing per manufactured part

Drawings and parts lists merge physically identical parts into ONE sheet /
ONE position with the total quantity — across all assemblies. That only works
when the model states identity correctly:

- Identical manufactured rows share one `partNumber` (column), also across
  child sheets; size variants get their own number (a formula such as
  `="QF-AP4040-"&E12` is fine). Different geometry or bore patterns never
  share a number. Validation reports `IDENTICAL_PARTS_DIFFERENT_PART_NUMBER`
  and `PART_NUMBER_SHARED_BY_DIFFERENT_GEOMETRY`; resolve both before claiming
  a fabrication-ready model.
- Bores are explicit invisible cylinder rows (`fastenerHoleCutter=true`) plus a
  `subtraction` naming the host. Keep a cutter within its host(s) (≤0.5 mm
  overhang): the drawing pipeline derives bores geometrically, so an overhang
  drills neighbouring parts (`HOLE_CUTTER_EXCEEDS_HOST`). List every part a
  bolt really passes through as host instead. Do not set `hostOutputId` on
  computed cutters — it snaps them onto a host face/edge.
- Fastener rows whose bore is modelled explicitly, nuts, T-slot screws, casters
  and hinges fixed with slot nuts get `cutEnabled=false`
  (`NUT_CUTS_NEIGHBOUR_PARTS`); otherwise every touched profile or panel gets
  a phantom hole.
- In-place subtractions keep the host id (the result of `door - opening` is
  still `door`); point later bore subtractions at the host id.

For Bauteilliste/Stückliste with prices or technical drawing planning, read the
“Priced BOM and drawing schedule” section in
[references/mcp-tool-contract.md](references/mcp-tool-contract.md).
Use `manufacturingPlan.deliverables` on `confbuild_plan_sheet_topology` and present

## Server selection and tool loading

- Use the hosted `confbuild` MCP server (`https://app.confbuild.com/mcp`). Only its tools drive the user's own signed-in editor tab and publish the live MCP connection/activity status shown in that tab. A repository-local development server (for example one registered as `confbuild-local`) renders in its own automation browser that the user never sees; use it only when the user explicitly asks to test a local server build, and never mix servers within one design session.
- When the host loads MCP tools lazily (Claude Code lists them as deferred tools), load the `confbuild` tool schemas through the host's tool search before the first call. A server that is still connecting is a reason to wait for it, never to switch to another server or to local scripts.
- Author Sheet rows and `scriptcode` directly in MCP tool arguments (`confbuild_create_project`, `confbuild_publish_checkpoint`, `confbuild_apply_sheet_patch`). Change an existing project script only through `patch_scriptcode` search/replace operations, never by resending the whole script. Do not write local generator or scratch scripts that assemble workbooks or scripts, and do not substitute repository generator loops (`scripts/create-*project.js`) for this workflow. Only deterministic repository tools named explicitly in this skill are exceptions.
- Perform the browser handoff in the browser that holds the user's signed-in confBuild session (in Claude: Claude in Chrome). An isolated browser without that login cannot claim the project tab, so the user would see neither the connection nor the progress.

## Hard browser boundary

The normal data path is always connected model → confBuild MCP tools → confBuild app/project state. All semantic project work belongs to MCP: create/clone, Sheet reads and patches, `patch_scriptcode`/`projectPatch.scriptcode`, validation, commit, render, and export. The connected editor tab rebuilds MCP-authored revisions, performs render/screenshot jobs, and shows coherent checkpoints to the user while work is in progress.

Host browser control is only a connection and tab-lifecycle transport for the action returned by `confbuild_prepare_browser` or the autonomous recovery exception below: `reuse`, `reload`, `navigate`, or `open-new`. During this handoff and the normal model loop, never click editor controls, type or paste project data, open or submit the AI prompt editor, invoke editor/page functions through evaluation or developer tools, or otherwise mutate project state. After the tab action, immediately return to `confbuild_prepare_browser` and the MCP `nextTool` flow.

Project-authored interactions are the explicit exception through the semantic MCP channel, not through host browser automation: use `confbuild_run_project_interaction` to exercise an exact persisted `INPUTID` button, a bare named project/VBA-script function, or an `API.registerAction` id in the exact prepared revision. Inspect its before/after images, changed-output evidence, and script diagnostics. Never substitute a raw DOM/editor click, `page.evaluate`, or an arbitrary expression for this tool.

Keep one active preview tab per project. Initial opening is single-shot; a stalled, disposable preview may be reloaded or replaced under Autonomous connection recovery below. A slow or dirty tab alone never authorizes duplicate tabs or loss of unsaved work.

When several Chrome/browser tabs are open, enumerate them before acting and prefer the tab whose URL matches the target project and saved configuration, even when another tab is focused, newer, or listed first. Use a signed-in dashboard only when no target-project tab exists, and create a tab only when neither a matching target tab nor the returned safe navigation target can be reused. Tab selection is scoped to the `designSessionId`: concurrent AI slots keep separate MCP transport connections, design/edit sessions, and retained browser-tab handles, so one slot must never switch, reload, or steal another slot's different project tab. Calls against the same edit session remain serialized; independent sessions/projects may run simultaneously.

An autonomous host handoff is mandatory whenever the host exposes Chrome/browser control. Before asking the user to open a link or answer "continue", discover and use the host's browser capability (for example Codex Chrome/browser control or Claude's configured browser tool). Treat the returned resource link as the agent's navigation target and only as a manual fallback. Match an already open tab by origin, project id, and saved-configuration id while ignoring query/hash differences such as `noCache`, `cacheBust`, `mcpBrowserHandoff`, `mcpRender`, and `part`; claim/reuse that tab even when its full URL string differs. Perform `open-new` automatically only when the handoff requests it and no matching tab exists. For a missing connection, follow the bounded connection recovery below before asking the user to intervene.

A UI fallback is outside the normal loop and must never be inferred from an MCP error, timeout, missing tab, or browser availability alone. It is allowed only when a structured MCP result establishes that the required semantic operation is unsupported, no MCP tool can perform it, and the user then explicitly approves the exact bounded UI action. Return to MCP immediately afterward. The confBuild AI prompt editor and provider-backed generation endpoints are never UI fallbacks because the connected model owns reasoning and content generation.

## Autonomous connection recovery

A disconnect is part of the authorized task. Recover it autonomously and resume the same project; do not require another “weiter”, a manual tab closure, or approval merely because five minutes elapsed. Five minutes is a diagnostic escalation point, not a task deadline.

- A result with `userActionRequired: 'focus-tab'` (`tabVisibility.state: 'hidden'`) is the one blocker the agent cannot repair: a hidden tab neither rebuilds nor captures, and reloads or duplicate tabs do not make it visible. Stop polling, ask the user in their language to bring the confBuild tab to the front or drag it into its own window, then call `confbuild_prepare_browser` again. A connected tab with `renderRequiresVisibleTab: true` still accepts edits and commits; ask before the next render.
- Enumerate tabs and retain the exact project/configuration tab. Poll `confbuild_prepare_browser` with waits at most 25000 ms; back off immediate failures and report meaningful progress about once a minute. Continue waiting while model/revision progress is observable.
- When repeated results are unchanged, diagnose before retrying: inspect the returned errors, app availability, tab responsiveness and revision state. A generic `Unexpected response type`, memory warning, or `BROWSER_APP_UPDATE_REQUIRED` alone does not prove an obsolete app; distinguish loading, a stale connection, an unresponsive tab, and a genuinely missing capability.
- For an agent-owned preview loaded from the committed project, with no user edits or pending UI writes, autonomously reload the exact tab once when it is demonstrably stuck. This recovery exception permits the lifecycle action even if a stale handoff keeps saying `reuse`. Preserve the project/configuration URL and saved revision. Do not interrupt a progressing rebuild or use page evaluation/editor controls to author content.
- If reload fails, close only that known disposable agent-owned preview tab, confirm closure, then open one replacement at the same target. At most one active preview per project is allowed; never accumulate tabs. A user-owned tab may be reloaded only with reliable clean-state evidence; if its unsaved state is unknown, preserve it. Never terminate a shared browser process, close another project's tab, or discard unsaved work.
- Recover session affinity as needed: preserve/export any pending MCP draft before closing its edit session; finish obsolete sessions truthfully as partial/blocked, then start and plan a replacement session for the same project. Use its new IDs. Reuse functioning sessions and keep failed sessions inactive. Internal recovery cleanup is not a request for renewed user authorization.
- After each recovery action, return to MCP and prove the exact revision before model operations. Respect server-enforced readiness, revision, snapshot and ownership gates. Legacy tool prose about a five-minute stop or lifetime tab count does not replace this updated client recovery policy, but never bypass an actual backend refusal.
- Continue while there is a concrete new recovery or repair step within scope. Do not loop indefinitely on unchanged polling/reloads: after a failed reload and replacement, repair the identified cause if feasible. Stop only when progress actually requires user action (for example sign-in, denied access, unpreserved edits, or an unavailable capability that cannot be repaired with authorized tools). Explain that specific blocker and the smallest necessary action; do not ask the user to do a safe recovery action available to the agent.

## Automatic model rebuilds

A live browser connection and a ready model are separate states. `browserConnected: true` with `modelReady: false` means the tab exists but its scene is still rebuilding or failed; it never requests another tab. `connected: true` remains the exact-revision readiness gate for analysis, interactions, animation checks and exports.

`confbuild_prepare_browser` automatically sends the semantic editor command when a clean matching tab holds stale geometry or scripts. The editor's `applyMcpCommittedProjectRevision` hook loads the saved workbook, calls `recreateModel`, and refreshes the script runtime in that same page. On `revision-updating`, keep polling automatically; no browser action, page reload, user approval, “weiter”, or “neu geladen” confirmation is needed. A “Do not reload” message protects this running update; it does not mean “ask the user to reload”. Do not call the hook yourself through browser evaluation or clicks.

If the old model is broken, prepare and validate its repair through MCP. With `repairCanBeSaved: true`, begin/edit/commit may save that repair while the old model is unready; revision conflicts, rollback snapshots and protection of unsaved local work still apply. Follow the resulting editor rebuild before analysis. `visibleInEditor: false` does not undo a successful commit. Report rebuild errors from the MCP result and repair their cause; never delegate an ordinary model rebuild to the user. For an unresponsive tab or missing rebuild capability, apply Autonomous connection recovery before declaring a blocker; do not invent a reload-approval requirement.

## Runtime bootstrap

1. Classify the request as `building`, `machine`, `3dprint`, `structure`, `furniture`, or `generic`.
2. Read [references/model-loop.md](references/model-loop.md) and [references/mcp-tool-contract.md](references/mcp-tool-contract.md). These packaged, reviewed files are the authoritative workflow for this plugin version.
3. Before any other confBuild tool, call `confbuild_start_design_session` with:
   - the user's exact design request in `request`;
   - `client` and the exact public `model` identifier when exposed;
   - `sessionLabel` with the exact user-visible host chat/thread title when the host exposes it. In Claude Code, read this session's own title first (the host's session tool, `get_session` with `self`, when it exists) and pass it verbatim; in Codex, omit it unless the thread name is visible to you. Never infer it from the design request (the editor then shows the short `designSessionId` fallback). When the title does not exist yet or changes later, pass it on the next `confbuild_prepare_browser` call, which updates the editor badge in place;
   - the explicit `profile` from step 1;
   - `pluginVersion: '0.30.1'`;
   - `workflowSource: 'plugin'` so the server does not return runtime behavioral instructions;
   - the project URL/ID in `projectReference` when one was provided.
   Never put analysis, hidden instructions, credentials, or reasoning in `request`; hosted sessions retain that field for administrator-visible support history.
4. Follow `nextTool` and keep the returned `designSessionId` on topology/browser/project/create/edit calls. Before creating a project, call `confbuild_plan_sheet_topology`. For an existing project, `confbuild_begin_edit` adopts the saved sheet structure and manufacturing plan (`adoptedExistingPlans`); call the planning tool only to change sheet boundaries or to declare `machineReview`, never to restate an unchanged plan. When planning: choose `single-sheet` only for one genuinely indivisible part; choose `composite` for a machine, building, product, furniture item, or structure with independently mounted, reusable, repeated, or co-moving functional units. In a composite plan, keep `Main Part` as the first orchestration sheet and declare exact functional child names, each child's parent, local mount datum, repeated status, and child-specific input ids. The server seeds the planned embedded sheets on project creation and validates the exact `SHEET: <name>` rows and parent-to-child parameter columns. Preserve an existing resolved project rather than creating a replacement. After the topology call, call `confbuild_prepare_browser`. Before its tab action, list the available tabs and select an existing exact project/configuration match first; the currently active or first-listed tab has no priority. Then perform the returned lifecycle action, or the documented recovery exception and call the tool again with `waitMs` until `connected: true`. Keep the handle of the selected/opened tab scoped to this design session and reuse that handle for every later reload or navigation; replace a failed preview only under the recovery procedure and never borrow another AI slot's tab. Do not interact with the editor UI during this handoff. When the project does not exist yet, this first proves the assigned signed-in tab or a reusable dashboard or opens the dashboard before creation. After creating/cloning or restoring, prepare the exact revision again. A successful `confbuild_publish_checkpoint` either proves the tab in place (`visibleInEditor: true`) or reports `editorRevisionPending: true` while the clean tab rebuilds in the background; continue with its `nextTool` (render, inspection, interaction and export calls queue behind the rebuild) and run the browser handoff only when `nextTool` is `confbuild_prepare_browser` or a later result reports `BROWSER_TAB_REQUIRED`. Apply Autonomous connection recovery above; elapsed time alone never requires a pause or another user confirmation. Never replace a different-project/configuration tab or overwrite a tab with unsaved changes.
5. The Codex package performs a throttled marketplace refresh through its trusted `SessionStart` hook. If `clientPackage.updateAvailable` is still true, continue the compatible task and give the supplied update command only as a manual fallback at handoff. Do not run an agent-driven self-update during the design task.

## Stable client responsibilities

- `confbuild_plan_sheet_topology` has two independent contracts: send `plan` for Main Part/child-sheet source ownership and send an explicit `manufacturingPlan` for stable product, definition, and physical occurrence identities. Never copy child-sheet boundaries blindly into `manufacturingPlan`.
- Load knowledge sections (`machine-domain-guide`, `machine-parts-guide`, `placement-conventions`, `pack-*`, `profile-*`) through `confbuild_get_prompt_sections` also in plugin sessions; only behavioral workflow sections are refused there.
- Machine sessions (profile `machine`) are gated: declare `machineReview` in `confbuild_plan_sheet_topology` before geometry — `safetyElementDecision` (scope-aware emergency stop: `required`, rationale, `safetyFunction`, operator-station `locations`) and `mountInterfaceDecision` (feet/base flange/clamp band/bracket with `type`, `host`, `fastening`, or `required: false` with a rationale). `completionState=complete` is refused without both (`MACHINE_REVIEW_REQUIRED`), and a required safety decision demands a native `emergencystop` row (`MACHINE_SAFETY_DEVICE_MISSING`) — never a primitive stand-in. Load the `machine-domain-guide`, `machine-parts-guide`, and `placement-conventions` prompt sections for machine targets, and verify persisted pose animations with `confbuild_validate_animation` (pose(0) no-op, pose(mid) motion, t=1 seam, reset fidelity) before claiming a working animation.
- Bind every generated physical row through valid `metadata_json`: definition, geometry, kind, process, sourcing, drawing policy, part number, and revision are local. Directly placed rows also carry `manufacturingOccurrenceId`; reusable child rows derive final part occurrences from the parent `manufacturingInstance` plus local `manufacturingGeometryRef`. Repeated instances reuse a definition id but never a final occurrence id. A returned `sheet-derived-legacy` plan is compatibility fallback, not completion-quality evidence.
- A geometry row is not automatically a part: when one manufactured part is modelled by several visible rows that no union fuses (a shaft row plus a flange row, a body plus a boss), give those rows the same `manufacturingPart` label, or the same `manufacturingOccurrenceId` with row-specific `manufacturingGeometryRef`, so the drawing editor draws ONE part sheet; such rows must share assembly, instance, kind, make/buy, and drawing policy. Union/subtraction results are already one part. Identical repeated parts keep separate rows and share only `partNumber`/`manufacturingDefinitionId`. The bill of materials counts such rows as ONE position and sums their weight and price, so state a bought part's price and datasheet mass on one of its rows only. Users may regroup parts later in the Drawing Editor's manufacturing-structure tree, which writes the same keys back into the sheet.
- Generate or patch Sheet rows and project `scriptcode` yourself through MCP tools. Never ask the confBuild prompt editor to generate them. Browser UI authoring is permitted only by the explicit capability-failure fallback gate above, never as a routine alternative to MCP.
- Default user-facing numeric INPUT rows to `slider` with sensible `MIN`, `MAX`, and `PARAMS` step values. Use `number` or numeric `textbox` only for a genuine arbitrary exact-entry requirement or when safe bounds are unknown; assess every `NUMERIC_INPUT_SHOULD_USE_SLIDER` validation warning.
- Match the Composite Model Loop's assembly structure. Group child sheets by physical serviceable unit rather than primitive type; model one repeated unit once and instantiate it through `SHEET:` rows; keep global placement in `Main Part`, local geometry around a stable mount datum in each child, and expose only that child's planned `INPUTID` values as matching columns on its parent reference row. A complex assembly flattened into `Main Part`, an orphan child, a cyclic reference, or a planned parameter missing from the parent row is incomplete even when the overview renders.
- Make long initial builds visible: create the seeded project early, then use adaptive coherent checkpoints (one for small models, usually 2–4 for medium models, assembly-boundary or 45–90-second intervals for large models). Prefer `confbuild_publish_checkpoint`; it patches, validates once, atomically saves the workbook and `scriptcode`, creates a mandatory rollback snapshot, and updates the connected clean tab in place. A snapshot failure blocks the commit instead of producing an unprotected revision. Use separate patch/validate/commit calls only for draft repair or compatibility. Never commit invalid partial geometry and do not render four views for every progress checkpoint.
- Treat deterministic validation and the packaged model loop's multi-view visual stop gate as mandatory before claiming completion. After a checkpoint, a `diagnosticsOnly: true` render is the cheap build check: act on `outputIdAudit.rowsWithoutGeometry` and `engineWarnings` before spending a multi-view render.
- For composite work, require validation `topology` to match the declared plan and require `diagnostics.scene.subsheets` to name every planned nested `SHEET:` child; counts alone do not prove the right children loaded. Follow `qualityGate.suggestedInspectionSubsheetNames` and call `confbuild_inspect_outputs` with those exact names until every child has evidence. A visible `Main Part` or whole-model screenshot never substitutes for a child-sheet inspection.
- Follow render `qualityGate` and `nextToolArguments` literally. For every multi-part revision and every planned child sheet, inspect all four returned images: opaque target with ghosted surroundings, isolated target, automatic center section, and x-ray. Treat each defect pair as its own local output-id group instead of combining distant findings in one frame. When diagnostics name suspect output IDs, use those exact IDs, repair the generating cause, repeat the affected inspection set on the repaired revision, and only then run the final unscoped four-view pass. A rejected `completionState: complete` continues the repair loop; it is not a finish-tool error to bypass.
- For `structure`, require the quality gate's series of up to three contact-derived connection targets rather than a largest-part overview: inspect each returned plate/bracket/anchor/fastener group or member joint close-up for seating, end cuts, hardware, clearance, and a continuous load path. Evidence for unrelated output IDs does not satisfy the gate.
- Prefer the deterministic repair operations over hand-written rows: every `TOPOLOGY_*` wiring error and every `PHYSICAL_MATERIAL_MISSING` warning that can be repaired carries a `suggestedOperation` (`wire_child`, `set_default_material`); `autoFix: true` on a patch or checkpoint repairs the INPUT contract and derives manufacturing metadata. Read `normalizations` on every patch, checkpoint and create result: it lists each rewrite the server made, including 0/1 number inputs turned into checkboxes.
- Treat `ROW_TYPE_HEADER_MISMATCH` as a real defect: the row reads another type's columns positionally and builds degenerate geometry without an engine message.
- Read `previousEngineCheck` on patch, checkpoint and validate results: from the `interfaces` stage on, every checkpoint starts a diagnostics-only engine check in the background and reports it once on the next call; repair `rowsWithoutGeometry` and actionable warnings before the next visual render.
- Before the inspection sweep and the final unscoped render, call `confbuild_finish_design_session` with `dryRun: true` and resolve its `blockers` in the listed order (commits first, then evidence, then the final render). Inspection evidence is bound to the revision, so an unchanged project keeps it across sessions.
- Results of patches, checkpoints and commits list each validation warning once per edit session; repeats appear only as `previouslyReportedWarnings` counts and unchanged topology as `{ unchanged: true }`. Use `confbuild_validate_edit` when the full list is needed. Early checkpoints (`scaffold`, `envelope`, `primary-assemblies`) may still lack the wiring of children not built yet; those findings are warnings with `deferredUntilStage: 'interfaces'` and block again from `interfaces` on.
- If a commit or checkpoint fails with `BROWSER_TAB_REQUIRED`, everything submitted stays in the edit session (`retainedInEditSession`). After `confbuild_prepare_browser` connects, retry with only the `editSessionId` and a new `mutationId`; never regenerate or resend the payload.
- Poll running jobs with the returned `nextToolArguments` (`waitMs` ≈ 25 s) and never start a second render/export for the same revision; a capacity error names the job ids to keep polling. Give `mutationId`s to patches/checkpoints so a retry after a client timeout is acknowledged instead of applied twice, and never issue two calls against one edit session in parallel.
- Lighting, sun position, environment map, background, fog, rendering mode, and view toggles are not sheet rows: they live in `project.sceneSettings`. Sheet rows can only ADD lights, so a scene that reads too bright, too dark, wrongly lit, or wrong-time-of-day is fixed with `confbuild_update_scene_settings` (or `projectPatch.sceneSettings` on a checkpoint/commit), never by adding a compensating negative light. Read the current values with `confbuild_read_project` plus `includeSceneSettings: true` before judging a render's lighting.
- When a row schema is unknown, call `confbuild_explain_row_type` for that type instead of loading the whole catalog pack.
- When the user asks for a control cabinet matching an existing machine ("Schaltschrank passend zur Maschine", correct components for the built-in drives/sensors/valves), do not hand-pick components: run the repository's deterministic deriver `node scripts/derive-electrical-cabinet.js --project <id>` (control platform defaults to the user's preferred open QiTech Control system - industrial PC + EtherCAT coupler/terminals, axes as DS402 slaves, hardwired safety, plus a `qitech-io-map.json` seed for the machine definition; pass `--platform classic` for a conventional PLC; on explicit request add `--control-code` - or run `node scripts/generate-qitech-control-code.js --plan <outDir>/plan.json` on an existing plan - to emit the downloadable QiTech Control machine package: Rust `machine_implementations/src/<slug>/` in the newest MachineNew/role-based pattern with EK1100 + EL1008/EL2008 + MinasA6BMotor, `machine.json` EEPROM roles and an INTEGRATION.md; `cargo check` in the target repo remains mandatory) (offline: `--workbook sheets.json`), then apply its emitted `Schaltschrank` child sheet via `upsert_sheet_tsv` plus the Main-Part `SHEET:` row (must pass the `door_open` parameter), extend - never replace - the manufacturing topology plan by `assembly-Schaltschrank`/`schaltschrank-enclosure`, and keep the `lod` cell on every dinpart row (otherwise the gear is build-deferred and invisible in whole-model renders). The tool's `report.md` documents inventory, sizing rules and assumptions; details in `docs/electrical-cabinet-derivation.md`.
- Inspect every returned render image and its diagnostics yourself. Screenshots are evidence, not decoration.
- Preserve the connected clean preview through normal checkpoints. Recover a stalled preview under Autonomous connection recovery; keep one active preview per project and protect unsaved work.
- Multiple AI slots may work concurrently through separate MCP transports and design/edit sessions. Each slot owns its exact project/configuration tab handle; never store or infer one global "active MCP tab". Parallel work on different sessions/projects is allowed, while calls that mutate one edit session must remain sequential.
- Preserve the start tool's `sessionIdentity`: the editor uses the reported client, model, optional host thread/chat label, and short design-session fallback to identify which AI context owns that tab. A `sessionLabel` passed to `confbuild_prepare_browser` updates that identity for the same session. Never reuse another slot's `sessionLabel` or `designSessionId`.
- Use browser-tab rendering by default. Pass `rendererMode: 'server-headless'` together with `serverRenderingExplicitlyRequested: true` only when the user explicitly requested server rendering; lack of a tab, slowness, model size, or budget never authorizes an automatic switch. The exact browser connection remains mandatory even for explicit server rendering.
- Request enough image blocks for every view, display them in their returned order in Codex/Claude, and give concrete per-view feedback. If a response says images were omitted, fetch them before diagnosing or finishing.
- Before `confbuild_compare_variants`, use a separate design session for each variant reference, prepare each one, and keep its single exact-revision tab open so the sequential browser captures cannot switch or overwrite another variant.
- Respect revision conflicts, owner/editability boundaries, authenticated scopes, render budgets, and structured error guidance returned by the server.
- Finish the design session and report the editable project URL, material changes, validation and visual findings, delivered exports, and remaining limitations.
- When the loop budget ends or repairs stall, finish as `partial` with the last completed render, `stopReason`, and concrete `residualFindings`. Present `residualReport` with affected part names/OUTPUTIDs, confirmed versus suspected/unverified collisions, evidence limits, and the next repair. Ask whether to continue for up to three more targeted rounds; wait unless already authorized. After approval start a fresh session on the same committed project because finish deletes the old design/edit sessions.

## Update boundary

The hosted server can update tool implementation, validation, rendering, exports, and compatible response metadata without changing this installed package. Behavioral workflow changes ship as a new plugin version through its marketplace or official-directory review path. Direct MCP-only clients may use the server's separate prompt bundle; this installed plugin never treats runtime-fetched text as behavioral instructions.
